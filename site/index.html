Two metrics, two boundaries

This tool reports two different classes of sustainability indicator. They are never added together, and neither validates the other.

Modelled CO2e
Estimated by CO2.js from transferred bytes. Covers data centre, network and a generic device. It is a model output, not a measurement.
Observed client energy
Energy drawn by Firefox's own processes while performing the workload, read from the Gecko Profiler's power counters in picowatt-hours. Measured on the machine running the test.

The measurement boundary is the client machine. Nothing here measures server, database, or data-centre energy, and no result is a total carbon figure for a site.

How it works

  1. 1 Describe the scan. Fill in the form; it opens a pre-filled GitHub issue for you to review and submit.
  2. 2 A runner measures it. A GitHub Action drives Firefox and records network, CO2e and timing data. Energy needs physical Apple Silicon hardware, so hosted scans omit it.
  3. 3 Results publish here. A summary is posted to your issue and the full result appears in the table below.

Request a scan

Scans are queued through the GitHub issue tracker. Nothing is filed without your confirmation — the form opens a pre-filled issue for you to review and submit.

Scan mode

Up to 20 URLs, each measured several times. Repetition is what makes a result trustworthy. Use this for comparisons.

Up to 200 pages from one start URL, measured once each. Good for discovery and ranking; a single run cannot separate a real difference from noise.

One public http:// or https:// URL per line. Maximum 20 per request.

Used as the issue title, e.g. "example.com landing pages".

Runner

Neither hosted runner can measure energy. GitHub's macOS runners are virtual machines, and Apple's Virtualization framework does not expose the SoC power-manager hardware to a guest — so Firefox's power counters exist but never produce a sample. Hosted scans report network, CO2e and timing only. Energy needs a physical Apple Silicon machine (a self-hosted runner, or the CLI locally).

More runs give a tighter result. 8 is a reasonable default; below 10 no statistical significance is claimed. Maximum 30.

Up to 200. A full 200-page crawl takes roughly 15 minutes.

A regular expression matched against the URL path, e.g. ^/admin. Leave blank to crawl the whole origin.

Viewport affects layout and rendering work, so it can change measured energy.

How to read these numbers

"Resolved" matters more than the number

A measurement is only reported when the effect is larger than its own run-to-run scatter, and the median exceeds idle. Lightweight static pages usually fail this test: they paint and the browser goes idle, so there is nothing to detect above the noise floor. Those rows show not resolved and no energy value, because publishing noise as a measurement would be worse than publishing nothing.

Where this tool works

  • Works well: CPU-heavy pages, authenticated application interfaces, interactions such as filtering or submitting a form.
  • Does not work: small static pages — use transferred bytes and request counts for those instead.

Shared runners are noisy

Scans run on GitHub's shared virtual machines, which have no thermal or noisy-neighbour control. They are good for capability checks and for network and CO2e metrics. Serious A/B regression work belongs on a dedicated machine.

Modelled and measured are not comparable

A page can transfer very few bytes and still burn substantial CPU. In testing, two pages of near-identical size differed by roughly 134× in measured energy while their CO2e estimates sat within 1.5× of each other. Rank by one metric or the other — never by their sum.
